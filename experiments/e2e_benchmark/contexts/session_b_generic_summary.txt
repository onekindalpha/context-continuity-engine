# Benchmark task (실제 coding continuation task, 5~10분 규모)

이전 버전의 task는 "CCE 자신을 baseline보다 효율적으로 만들어라"는 meta-task였다 —
CCE가 CCE를 고치는 자기참조적 과제라 "새 세션이 실제 coding을 이어받아 완수하는가"를
보는 목적에 맞지 않았다. 이번 버전은 크기와 판정 기준이 분명한, 실제로 존재하는
작은 버그 하나를 고치는 task로 바꿨다.

## 배경 (실제로 확인된 버그)

`src/context_analysis.py`의 `_make_summary`는 COMPRESS 항목의 요약을 만들 때
`SUMMARY_MAX_CHARS`(40자)에서 그냥 글자 수로 자른다:

```python
def _make_summary(text: str) -> str:
    collapsed = " ".join(text.split())
    if len(collapsed) <= SUMMARY_MAX_CHARS:
        return collapsed
    return collapsed[:SUMMARY_MAX_CHARS].rstrip() + "..."
```

이 방식은 단어 중간에서 잘릴 수 있다. 실제 예시(직접 실행해서 확인함):

```python
text = "This paragraph intentionally uses a longish nineteencharacters word here to test truncation"
# 현재 동작: "This paragraph intentionally uses a long..."  <- "longish"가 "long"으로 잘려서
#           원문에 없던 다른 단어처럼 보인다.
# 기대 동작: "This paragraph intentionally uses a..."        <- 단어 경계에서 자른다.
```

## 지시문 (LLM에게 그대로 전달되는 문장)

> `context-continuity-engine` 프로젝트의 `src/context_analysis.py`에 있는 `_make_summary` 함수를 고쳐라. 지금은 `SUMMARY_MAX_CHARS` 위치에서 그냥 글자 수로 잘라서, 단어 중간이 잘려 원문에 없던 다른 단어처럼 보이는 경우가 있다(위 "배경" 예시 참조). 요약이 잘릴 때 **단어 경계(공백)에서** 자르도록 고쳐라. 단, 다음을 반드시 지켜야 한다:
> 1. `python3 -m unittest discover -s tests`가 전부 통과해야 한다(기존 테스트를 깨면 안 된다).
> 2. 자를 위치를 찾을 수 없는 경우(예: 공백이 전혀 없는 40자 넘는 긴 문자열 하나)에는 기존처럼 글자 수 기준으로 잘라라 - 무한루프나 빈 문자열을 반환하면 안 된다.
> 3. 이미 `SUMMARY_MAX_CHARS` 이하인 텍스트는 그대로 반환한다(기존 동작 유지).
> 코드를 수정한 뒤 테스트를 직접 돌려서 확인하고, 통과하면 종료해라.

## 판정 기준 (자동, harness.py가 실행 - LLM 자기 보고를 믿지 않는다)

1. `python3 -m unittest discover -s tests` exit code == 0.
2. harness가 직접 작성한 acceptance check(`_word_boundary_ok`, `harness.py` 참조)를 worktree에서 실행해서:
   - 공백이 있는 긴 문자열 예시에서 단어 경계로 잘리는지 확인.
   - 공백이 없는 긴 문자열 예시에서는 기존처럼 글자 수 기준 fallback이 동작하는지 확인(이 조건이 깨지면 안 된다).

두 조건을 모두 만족해야 `task_success = true`.

## 왜 이 task인가

- 실제로 코드에 있는, 지금 이 순간 참인 버그다 - 조작된 예제가 아니라 직접 실행해서 확인했다.
- 크기가 작다: 함수 하나, 대략 5~10분 안에 사람도 고칠 수 있는 규모다 - "무거운 25라운드짜리
  실험"이 아니라 결정적으로 끝나는 task를 원한다는 피드백을 반영했다.
- Context 의존성이 있다: 이 task를 안전하게 풀려면 "공백이 없는 경우의 fallback을 반드시
  남겨둬야 한다"는 함정을 알아야 한다 - 이건 Session A/B/C의 메모리에 포함된 이전 논의에서
  다뤄진다. Context가 부실하면 fallback 처리를 빠뜨려서 조건 2를 놓칠 가능성이 있다 - 이게
  "이전 결정/함정이 보존되는가"를 실제로 측정하는 지점이다.
