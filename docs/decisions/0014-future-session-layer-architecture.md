# 0014. 향후 확장 방향: Session Memory / Session Log 분리 아키텍처

## 상태

로드맵(구현하지 않음, 문서화만)

## 배경

사용자가 다음 아키텍처를 제안했다: LLM(Claude/GPT) API를 그대로 쓰되, 그 앞에 별도의 Session Layer를 두어 (1) Session Memory — Redis 같은 캐시에 TTL로 보관되는 "현재 세션 상태", (2) Session Log — 사용자가 "저장 ON"을 선택했을 때만 DB/Object Storage에 영구 보존되는 과거 기록, 이 둘을 분리한다. Context Builder가 Session Memory(+필요시 Session Log에서 추출한 내용)로 매 호출마다 `system` 메시지를 만들어 LLM API를 호출한다.

## 판단: 아이디어 자체는 타당하다

이건 실제 LLM 서비스들이 흔히 쓰는, 검증된 패턴이다(LLM = 추론 엔진, 별도 계층 = 기억 관리). 그리고 이 프로젝트의 기존 설계와도 개념적으로 정확히 맞아떨어진다:

- 이미 `importance`(장기적으로 중요한 정도)와 `task_relevance`(지금 이 episode에 관련된 정도)를 분리해서 계산하고 있다(`docs/decisions/0005` 등) — 이게 정확히 "Session Memory(현재 episode) vs Session Log(장기 기록)" 구분과 같은 아이디어다.
- `retention_action`의 `EXTERNALIZE`는 "지금 context에는 안 넣지만 어딘가에 보관해서 필요하면 꺼내 쓴다"는 결정인데, 이게 바로 "Session Log에 저장 + 필요시 추출"에 해당한다. 지금은 이걸 실제 storage 없이 값(문자열)으로만 표시하고 있을 뿐이다.

즉 사용자가 제안한 구조는 이 프로젝트가 이미 암묵적으로 따르고 있던 설계 방향을 명시적인 서비스 아키텍처로 확장한 것이다.

## 판단: 지금(마감 임박 시점) 구현하지는 않는다

이유:

1. 현재 프로젝트는 저장된 session log 파일 하나를 오프라인으로 분석하는 CLI/라이브러리다(`docs/decisions/0001`, `0011`에서 실시간 연동을 이미 명시적으로 범위에서 제외). 제안된 구조는 이것과 완전히 다른 종류의 산출물이다: 상시 실행되는 서버, Redis, DB, Claude/OpenAI API 프록시, 사용자별 세션 관리, 인증 — 사실상 별도의 백엔드 서비스 하나를 새로 만드는 일이다.
2. 이 sandbox에는 LLM API 키가 없다(`docs/decisions/0006`에서 이미 확인된 제약). 실제 API 호출 계층을 만들어도 검증할 방법이 없다.
3. 지금까지 만든 것(규칙 기반 파이프라인, baseline 비교, reconstruction test, CLI, 94개 테스트)은 전부 실제로 동작하고 정직하게 측정됐다. 마감 이틀 전에 완전히 다른 인프라를 새로 시작하면, 검증된 결과물을 완성하지 못한 채 마감을 맞을 위험이 크다.

## 결정

이 아키텍처를 "다음 로드맵"으로 문서화한다(이 문서). 결과보고서의 "향후 계획"에도 반영해, 지금 만든 규칙 기반 분석 엔진이 이 Session Layer의 "Context Builder" 부분에 그대로 재사용될 수 있다는 것을 명시한다 — `build_working_context()`가 이미 하는 일(현재 memory에 뭘 넣을지 결정하는 것)이 Context Builder의 핵심 로직과 동일하기 때문이다.

## 알려진 한계 (이 로드맵 자체의)

- Redis TTL 기반 설계는 "세션이 만료되기 전에 사용자가 저장 여부를 결정하지 않으면 데이터가 사라진다"는 엣지 케이스가 있다 — 저장 여부를 세션 시작 시점에 미리 물어보거나, 만료 직전에 한 번 더 확인하는 흐름이 필요하다(설계 시 보완 필요, 아직 결정 안 함).
- 여러 LLM 제공자(Claude/GPT)를 오가려면 각 API의 메시지 형식 차이(예: system 메시지 처리 방식)를 흡수하는 어댑터가 필요하다 — "코드 한 줄만 바꾸면 된다"는 단순화는 실제로는 더 복잡할 수 있다.
